# AGENTS.md

How this codebase wants to be written, and where it does not yet live up to that. Setup, branching, PRs and releases are in `CONTRIBUTING.md`, `COLLABORATING.md` and `collaborating/`. Three principles govern everything below: tight opinionated design, intent visible in the code, and a single source of truth. The codebase is mid-migration toward all three, so prevalence is not a guide; when old and new code disagree, follow the principle and the newest code that follows it.

## 1. Tight, opinionated design: the app composes, the library styles

- The design philosophy lives in `packages/ui/README.md` (Design System Philosophy, UI Layout Concepts). Read it before touching layout. The one governing idea: the container owns the space, children never manage their own margins, and app code composes primitives rather than styling them.
- The end state is that `app/` contains no manual styling at all; the library is not mature enough yet and the UI not consistent enough to enforce that, so follow it whenever possible and treat every remaining `styles.module.css` under `app/` as debt, never as a pattern to copy.
- Start every arrangement from the primitives: `Container` (section boundary with header/content/footer), `ListView` (`layout="inline" | "block" | "grid"`, the list owns spacing), `InlineLayout` (`before`/content/`after`), `InlineView` (adaptive variant of InlineLayout), `BlockView` (header/content/footer stack), `InputSection`, `ButtonLayout`. Read their props from `packages/ui/src/components/<Name>/index.tsx`; `packages/ui/dist` is build output and is often absent or stale.
- When a view needs a variation the library lacks, the first move is to add it to the component in `packages/ui` with a changeset, as `43d6900c6` did with `withContentMaxWidth` on `Description` in twelve lines. A local CSS module is the last resort and carries a `FIXME` saying what the library is missing.
- Values are tokens: `spacing`, `textSize` and friends take scale tokens, never CSS values; CSS files use `var(--go-ui-*)` from `packages/ui/src/index.css`, never px or hex. If the scale lacks a value, extend the scale in the library.
- Model app-side composition: `app/src/components/domain/DrefKeyResources/index.tsx` (data array mapped into `Container` cards inside a `ListView` grid, no CSS) and `app/src/views/DrefAnticipatoryPillar/index.tsx`.
- Where the library is heading: `origin/project/go-ui-restructure` (GO UI v3) declares the layer model (raw → generic → specific, imports point downward), token specs, single `variant` on specific components, HTML/ARIA-aligned names and native-semantics-first accessibility. Its `packages/ui/CONTRIBUTING.md` and `MIGRATION.md` are the statement of intent; do not import from that branch, but when `develop` and the branch disagree on direction, the branch wins.

### Old versus new: the migration is not finished

- The UI was re-platformed in commit `09e2d2ee7` (2025-09-02, "Revamp UI components", `@ifrc-go/ui` 2.0.0). Many components exist in a pre-revamp and a post-revamp form, the old one usually has more callers and sits in the more discoverable place, and a recent last-touched date proves nothing because old code still gets maintenance commits.
- Tell them apart by what they do, then confirm by first-added date: post-revamp code has no layout CSS, a `TabPage` root for form tabs, `#components/printable/*` for exports, types from `#generated/types`, strings from `i18n.json` rather than `// FIXME: use strings`. `git log --diff-filter=A --format=%ad --date=short -- <dir> | tail -1` on both candidates, and check which one `app/src/views/EapFullForm/` (2025-10), `EmergencyOverview/` (2026-04) or the `Dref*` landing pages (2026-08) use.
- Worked case: `app/src/components/domain/SourceInformationInput/` (2023; type imported from `#views/DrefApplicationForm/schema`, flex CSS module, `Button styleVariant="action"`) versus `app/src/views/EapFullForm/EAPSourceInformationInput/` (2025-10; type from `#generated/types`, `Container` and `ListView`, `IconButton`, no CSS). Never import the domain one outside the DREF forms; start from the EAP one. Never import `#views/...` from `app/src/components/` at all.
- Of the four same-named DREF form trees, `app/src/views/DrefApplicationForm/` is the most converted. `OldDrefFinalReportForm/` and `OldDrefFinalReportExport/` are a frozen legacy copy (see the TODO in `app/src/App/routes/index.tsx`): never a template, never the first place to make a change.
- New PDF/export views copy `app/src/views/EapFullExport/` and `#components/printable/*`, not `DrefApplicationExport/`. `Grid`, `Header`, `Footer`, `BodyOverlay`, `FilterBar`, `Overlay`, `useBasicLayout` and `useSpacingTokens` no longer exist in `@ifrc-go/ui`.

## 2. Intent visible in the code

- Code should read without trivial comments: names say what a thing is for, and a complex condition or transformation becomes a function or a named value whose name explains it. Pattern from `a3722a87a` in `app/src/views/EmergencyOverview/index.tsx`: compound JSX conditions became `showEarlyWarningKeyFigures`, `showEventKeyFigures`, `showSituationalOverview`. Pattern from `app/src/utils/domain/dref.ts`: `sanitizeGlideCodes`, `getNewDrefRouteState`. Do not over-extract; a one-line expression with an obvious meaning stays inline.
- Comments explain why, never what: a server quirk, a product decision, a constraint. Prefix them `NOTE:`, `TODO:` or `FIXME:`, and `FIXME(<name>):` when it is a known personal follow-up (`64d0d1b16` is the shape: `// NOTE: server drops operational_update_details for users without region admin access`).
- Prefer data plus a map over repeated JSX (`DrefKeyResources` builds a `resources` array, then renders it). Prefer derived values over state set in effects; the React Compiler lint rules (`react-hooks/set-state-in-effect`, `react-hooks/refs`, `react-hooks/immutability`) are errors, and new code omits manual `useMemo`/`useCallback`.
- Null handling is `isDefined`/`isNotDefined`/`isTruthyString` from `@togglecorp/fujs` and defensive defaults (`?? []`), never `!= null`. Class names merge with `_cs` from the same package.
- A routed view exports `export function Component()` (with the `import/prefer-default-export` disable); the loader in `app/src/utils/routes.tsx` destructures `Component`, so a default export breaks the route. Everything else is `function Name(props: Props)` + `export default Name;` in `Name/index.tsx`.
- Links are `#components/Link` with `to="<route key>"` (a key of `WrappedRoutes`, never a path) or `external href=`; navigate with `useRouting().navigate()`, never react-router's `Link`/`useNavigate`. No raw `<a>`, `<button>`, or `onClick` on a `<div>`. A `DropdownMenu` holding actions renders `#components/DropdownMenuItem` entries; it is what closes the menu.
- Icon-only controls need a text name and lint will not tell you (`jsx-a11y` runs with `controlComponents: []`): `IconButton` forces `title` and `ariaLabel`; an icon-only `Button` or `Link` needs `title=`.
- Commits are `type(scope): imperative summary` with a bulleted body of what changed (`fec4d09f8`); changesets describe the change from the user's perspective (`.changeset/`). Never hard-wrap prose anywhere.

## 3. Single source of truth

- The OpenAPI schema is the source for API types: `app/generated/*.ts` is gitignored output of `pnpm generate:type` from the three submodules (the patched `openapi-typescript` 6.5.5, never `npx openapi-typescript`). Never edit it; when the API lacks a field, bump the submodule gitlink in the same PR. `initialize:type` copies `app/types.stub.ts` only when a file is missing, so a stale file survives until you regenerate.
- All HTTP goes through `app/src/utils/restRequest/index.ts` (`useRequest`, `useLazyRequest`, `useRiskRequest` with `apiType: 'risk'`), typed with `GoApiResponse`, `GoApiBody`, `GoApiUrlQuery`, `RiskApiResponse` and a literal `url`. Never index `paths[...]` from `#generated/types`, import `@togglecorp/toggle-request`, or call `fetch`. A direct `components<...>['schemas'][X]` reference needs a mode: `'read'` for server data, `'write'` for request bodies.
- Server enums come from `useGlobalEnums()`, never hardcoded lists; a compared key is a named constant typed `N satisfies <EnumKey>` (`app/src/utils/constants.ts` for shared ones, the feature's `common.ts` or `app/src/utils/domain/<feature>.ts` for local ones).
- The form schema is the authority on a field: what it is, when it applies, what happens when hidden. Today the UI sometimes re-decides visibility on its own; that divergence is a known gap being closed, not a pattern. Template for a multi-tab form: `app/src/views/EapFullForm/` (`schema.ts`; `common.tsx` with per-tab field lists and `checkTabErrors`; one directory per tab). A field added to `schema.ts` must also join its tab's list, or the tab never shows an error marker.
- Form types derive from the body: `GoApiBody<'/api/v2/x/{id}/', 'PATCH'>` → `PurgeNull`/`DeepReplace` → `PartialForm<..., 'client_id'>`; never `GoApiResponse` as a body type. Arrays of objects carry `client_id` everywhere: `keySelector: (item) => item.client_id`, member fields `client_id: {}, id: { defaultValue: undefinedValue }`, `injectClientId` on load, `{ client_id: randomString() }` on add, child errors via `getErrorObject(errorFromProps?.[value.client_id])`.
- Conditional fields use `addCondition(...)` inside `fields()` and return `{ forceValue: nullValue }` when hidden (sends null, clears the server value); `undefinedValue` omits the key so the server keeps the stale value, so it is only for client-only fields such as `confirm_password`. Submit through `createSubmitHandler(validate, setError, onValidated)` and shape the payload in `onValidated`; never hand-roll `validate()` + `setError(result.error)`. Server errors: `setError(transformObjectError(formErrors, getKey))` from `#utils/restRequest/error` with `matchArray(locations, ['field', NUM])` mapping indices back to `client_id`. Required strings pair `required: true` with `requiredValidation: requiredStringCondition`; plain `required` accepts whitespace. Validation messages in `schema.ts` are English literals; do not call `useTranslation` there.
- `i18n.json` is the source for strings and the translation server derives from it through migrations. Each directory owns one `i18n.json` (`{ "namespace", "strings" }`), imported only from that directory as `import i18n from './i18n.json'` and read via `const strings = useTranslation(i18n);` at the top of the component. Namespace is set by location and checked by `pnpm translatte:lint`: `components/domain/<Top>/**` → lowerCamel(Top) even when nested; other `app/src/components/**` and all of `packages/ui` → `"common"`; `views/<View>/i18n.json` → lowerCamel(View). Keys are unique per namespace across all its files, not per file; the runtime merge is last-writer-wins and only translatte lint notices, so grep first.
- Any `i18n.json` change needs exactly one new migration per PR, generated last with `pnpm translatte:generate` into repo-root `translationMigrations/` (not `app/src/translationMigrations` as two docs say). Never hand-edit one; to fold in later edits, delete yours and regenerate. Exit 1 with "Nothing to do" means already in sync. Placeholders are `{name}`, filled with `resolveToString` / `resolveToComponent` from `@ifrc-go/ui/utils`; never build sentences with template literals.
- `app/scripts/eslint/i18n-usage.ts` (warn level, every `*.json` under `app/src`) autofixes by deleting any key it cannot see, and it only recognises the exact shape above: an arrow-function component, a wrapped default export, a destructured `useTranslation` or `strings[dynamic]` makes every key look unused. `pnpm lint:fix` applies it; review every deleted key in the diff.

## Verification

- Mirror `.github/workflows/ci.yml`: `git submodule update --init --recursive`, `pnpm install`, `pnpm build:ui`, `pnpm generate:type`; in `app/`: `pnpm typecheck`, `pnpm lint:js`, `pnpm lint:css`, `pnpm lint:translation`, `pnpm test`; in `packages/ui/`: `pnpm typecheck`, `pnpm lint:js`, `pnpm lint:css`; at root: `pnpm lint:unused`. Root has no `typecheck` or `test` script, `pnpm lint` does not run knip, and there are no git hooks. On a clean `develop` every tool reports 0, so a finding that survives real types, `dist` and `.env` is yours. The app resolves `@ifrc-go/ui` from `dist` only: rerun `pnpm build:ui` after any `packages/ui/src` edit.
- Environmental, not bugs: `TS2307 Cannot find module '@ifrc-go/ui'` (no dist); `TS2344 ... constraint 'never'`, `TS2315 'components' is not generic` and thousands of `'never'` errors (stub types, which every `pre*` script installs via `initialize:type`); stylelint `ENOENT ... @ifrc-go/ui/dist/index.css`; vitest `Failed to validate environment variables` (`app/.env` needs the keys in `app/env.ts`; copy the CI `env:` block); knip `Unresolved imports (51)` and eslint `import/no-unresolved '#generated/*'` with 41 fixable `import/order` errors (no `app/generated/`; run `pnpm initialize:type` in `app/` and never `eslint --fix` directly without it).
- A green `pnpm build` proves nothing about types: `app/vite.config.ts` has the TypeScript checker commented out and the CI build job does not depend on typecheck. `pnpm lint:unused` (knip, root only) is a hard gate on unused files and exports. `typos` (config `typos.toml`) hard-fails on misspelt `i18n.json` values. The `translation` jobs are `continue-on-error`; `typos`, `lint`, `typecheck` and `unused` are not.
